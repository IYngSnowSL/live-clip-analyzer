# 新功能分析：字幕驱动场景切分（主功能）

> 状态：设计讨论中，**尚未实现**。本文整理现有能力与可能存在的问题，供决策参考。
> 目标：以**完整视频的字幕（ASR 转写全文）为主要依据**，整理分析字幕内容，
> 一段一段地切出"场景"并截取切片；弹幕、画面等作为**辅助**信息存在。

---

## 1. 现状盘点：现有流水线对字幕驱动切分的复用性

当前 v0.2.1 的流水线是**视觉驱动**的：画面变化（PySceneDetect / FFmpeg 场景滤镜）
决定 8~30 秒的场景边界，随后叠加弹幕统计、画面理解与逐段 LLM 分析。

新功能把"边界来源"从**画面变化**换成**字幕语义**，其余环节大量可复用：

| 环节 | 现有模块 | 对字幕驱动切分的复用性 |
|---|---|---|
| 视频信息探测 | `ffprobe_info` | ✅ 直接复用 |
| 音频提取与分块 | `extract_audio_chunks` | ✅ 直接复用（ASR 的前置） |
| **全量语音转写** | `transcribe_chunks` | ✅ **主功能地基，已具备**：分块转写、时间戳合并、单块失败跳过 |
| ASR 容错 | `_transcribe_one` 多格式回退 | ✅ 直接复用 |
| OpenAI 兼容客户端 | `AIClient`（重试 / json 模式回退） | ✅ 直接复用 |
| 按时间段收集 ASR 文本 | `gather_asr_for_scene` | ✅ 思路复用（改成滑窗即可） |
| 原话时间戳定位 | `find_quote_time` | ✅ 直接复用 |
| 弹幕热度 / 情绪 | `danmaku` | ✅ 辅助评分源 |
| 画面描述 | `vision` | 🟡 可选辅助源 |
| 长切片候选合并（高分段聚合、时长约束、切块） | `generate_long_candidates` | ✅ 可直接跑在"语义场景"之上 |
| 综合评分加权框架 | `scorer` | ✅ 权重重排即可 |
| 切片导出（快切 / 精切 / 批量） | `exporter` | ✅ 完全不动 |
| 任务状态机 / 进度上报 | `task_runner` | ✅ 框架不动，插入新阶段 |
| 数据库结构 | `scenes` / `candidates` 表 | 🟡 字段基本够用，可能需加"话题 / 父场景"字段 |
| Web 复核 / 导出链路 | `api` + `web` | 🟡 场景概念变化后 UI 文案与交互需跟进 |
| Markdown / JSON 报告 | `report` | 🟡 小改（场景标题语义变化） |

**结论**：ASR 全文转写、LLM 分析、候选生成、导出这条"脊柱"已经存在；
真正需要新建的是**字幕整理模块**与**语义切分器**，以及配套的提示词与权重调整。

---

## 2. 需要新建的部分

1. **字幕整理模块**：ASR 全文的清洗与结构化（分段、字数与话题关键词统计、去重）。
2. **语义切分器**（核心难点，技术路线待定，见 §4）：
   - 方案 a：LLM 滑窗边界检测——窗口 5~10 分钟、带重叠，让 LLM 输出话题切换时间点；
   - 方案 b：便宜预筛 + LLM 精修——先用 TextTiling / embedding 相似度谷点找出候选边界，
     只对候选附近调用 LLM 确认；
   - 方案 c：两级层次——先粗切"话题段"（10~30 分钟），再在段内做"切片友好"细切。
3. **语义场景分析提示词**：以字幕为主、画面与弹幕为辅的字段化输出（标题 / 概述 / 评分 / 引用）。
4. **ASR 结果缓存读取**：目前转写结果虽写入 `asr.json`，但重跑任务不会复用，
   需支持"已有转写则跳过 ASR"。
5. **评分权重重排**：字幕内容权重上升（有趣度、高光潜力），弹幕降为辅助。

## 3. 可能存在的问题清单

### 3.1 ASR 层（地基风险）
| # | 问题 | 说明 |
|---|---|---|
| P1 | **时长成本** | 几小时直播全量转写耗时可达数十分钟，取决于接口速度 |
| P2 | **金钱成本** | ASR 按音频时长计费；每次重跑若不复用缓存会重复计费 |
| P3 | **识别质量** | 直播有 BGM、多人说话、游戏音效 → 错字、漏句、断句漂移；时间戳误差可达数秒 |
| P4 | **口语与混合语言** | 网络用语、语气词、中英混杂；需确定 language 参数策略 |
| P5 | **无音轨视频** | 字幕驱动完全失效，必须有画面 / 弹幕兜底路径 |

### 3.2 切分算法层（核心难点）
| # | 问题 | 说明 |
|---|---|---|
| P6 | **上下文窗口** | 几小时字幕全文（几万~几十万字）不可能一次进 LLM，必须滑窗 / 层次化处理 |
| P7 | **"场景"语义未定义** | 话题切换？情绪高潮？游戏对局？不同直播类型边界标准完全不同，这是最需要先拍板的问题 |
| P8 | **粒度控制** | 切太碎（每句话一段）或太粗（整场一段）都不可用；需要两级结构（话题段 → 切片段） |
| P9 | **LLM 输出不稳定** | 同段字幕两次调用边界可能不同；需要约束为"引用字幕行 + 时间戳"的锚点输出格式 |
| P10 | **边界对齐** | LLM 给出的是字幕行，需映射回 ASR 时间戳，再对齐到关键帧（导出层已有快切/精切语义兜底） |
| P11 | **切片完整性** | 纯按话题切可能切出"没头没尾"的片段；长切片需要起承转合，不能只按语义 |

### 3.3 成本 / 性能层
| # | 问题 | 说明 |
|---|---|---|
| P12 | **多级 LLM 调用成本** | 粗切 1 次 + 每场景精分析 N 次；场景上百时 token 开销可观 |
| P13 | **全流程耗时** | ASR + 切分 + 精分析串起来，几小时视频要跑多久？是否可接受 |
| P14 | **失败重跑** | 切分与精分析结果是否缓存，重跑只补失败场景 |

### 3.4 工程 / 数据层
| # | 问题 | 说明 |
|---|---|---|
| P15 | **与视觉场景的关系** | 现有 8~30 秒视觉场景是替换掉，还是与新"语义场景"并存为两级？旧任务数据如何兼容 |
| P16 | **断点续跑** | ASR 缓存、切分缓存、精分析缓存的分级设计 |
| P17 | **评测困难** | 切片好坏主观、无测试集；窗口大小 / 阈值 / prompt 全靠人工调 |
| P18 | **UI 跟进** | 时间轴要展示语义场景与边界理由；筛选 / 复核 / 导出交互需同步调整 |

### 3.5 产品层
| # | 问题 | 说明 |
|---|---|---|
| P19 | **视觉信息去留** | 纯字幕驱动会丢失换游戏、换歌、切屏等画面事件；视觉检测是降级为"辅助边界信号"还是完全移除 |
| P20 | **内容类型差异** | 游戏 / 聊天 / 唱歌 / 带货的边界标准不同，可能需要内容类型参数 + 不同 prompt 模板 |
| P21 | **输出形态** | 话题段（大）→ 高光切片（中）→ 单句素材（小）的三级结构是否需要一次做齐 |

## 4. 设计决策记录（2026-09-01 采访更新）

| # | 决策点 | 用户答案 | 状态 |
|---|---|---|---|
| 1 | 视觉切分去留 | B：并存两级（视觉"镜头段"保留 + 字幕"内容段"上层） | ✅ 已确认 |
| 2 | 场景语义与切片粒度 | C：两级都要（话题段导航 + 切片友好片段交付） | ✅ 已确认 |
| 3 | 分析什么类型直播 | 混合类型（游戏 / 聊天等不限定） | ✅ 已确认 |
| 4 | 输入规模 | 直播录播，1~4 小时 | ✅ 已确认 |
| 5 | 切分技术路线 | C：层次化两级（先粗切话题段，再段内细切） | ✅ 已确认 |
| 6 | 数据模型 | B：新建 `topic_segments` 表（scenes / candidates 保持不动） | ✅ 已确认 |

### 4.1 由输入规模推导的约束（Q4：1~4 小时直播录播）

- ASR 全量转写是固定前置 → **转写结果必须缓存**（对应 P2 / P16），重跑不重复计费。
- 音频按 20 分钟一块切，4 小时 ≈ 12 块，块级并发可显著缩短 ASR 耗时。
- 全流程目标建议：离线批处理，总耗时 ≤ 视频时长的 1/2（4 小时片 → 2 小时内出结果）；
  ASR、粗切、精分析按流水线重叠执行。
- 4 小时字幕全文约 3~6 万字：粗切必须分窗处理，精分析按场景并发。

### 4.2 混合内容类型的应对（Q3）

- 不写死单一 prompt 模板：通用"直播内容语义切分"提示词为底，
  预留内容类型参数（游戏 / 聊天 / 唱歌 / 带货）做微调。
- 边界判定标准取各类直播的交集：话题切换、情绪高潮、事件转折。

### 4.3 Q6 数据模型决策（已确认：方案 B）

**结论**：新建 `topic_segments` 表；`scenes`（镜头段）与 `candidates`（候选切片）保持不动。

**方案 A：复用 `scenes` 表，加层级字段**

在 scenes 加 `level` / `parent_id` 字段，话题段与镜头段混在同一张表。

- 缺点 1（字段语义错位）：话题段一行里 `quote`、`visual_summary`、
  `danmaku_*` 等字段要么空置要么含义扭曲；`get_scenes` API、报告、UI 渲染
  处处要加 `if level == topic` 判断，改动面反而更大。
- 缺点 2（约束冲突）：`UNIQUE(task_id, scene_index)` 假设"每个任务一条平铺时间轴"，
  两级结构需要改复合唯一键 + 迁移旧数据。
- 优点：少一张表、少一次 JOIN。但本项目的关联本来就是"按时间范围"而非外键，
  少这张表换不来多少便利。

**方案 B：新建 `topic_segments` 表（推荐）**

三个概念各居其位，职责互不干扰：

| 概念 | 存放处 | 颗粒度 | 用途 |
|---|---|---|---|
| 话题段 | **新建 `topic_segments` 表** | 几分钟~几十分钟 | 内容导航、目录结构 |
| 镜头段 | 现有 `scenes` 表（不动） | 8~30 秒 | 底层时间轴、弹幕统计（Q1 并存两级） |
| 切片友好片段 | 现有 `candidates` 表（不动） | 30 秒~3 分钟 | 可传播切片，走"复核→导出"链路 |

- 优点 1（零迁移）：scenes / candidates 及其全部消费方（API、UI、报告、导出）不用改，
  新功能纯增量。旧任务没有话题段数据时 UI 退化为现状显示，渐进升级。
- 优点 2（独立演进）：话题段未来加字段（情绪曲线、BGM 事件、说话人）不影响 scenes。
- 优点 3（查询干净）：话题段表字段少而专用（title / summary / keywords / score），
  报告单独渲染章节，不用到处过滤 level。
- 代价：多一张表、多一段建表与访问代码——成本很小。

**类比**：一本书——目录页（话题段表）≠ 正文段落（scenes 表）≠ 金句摘抄卡片（candidates 表）。
把目录硬写进段落表里，翻每一页都要问"你是目录还是正文？"

**推荐**：**方案 B**。等你拍板后写入正式决策。

## 5. 建议的演进顺序（按已确认决策更新）

1. **地基**：ASR 结果缓存读取 + 字幕整理模块 + 新建"话题段"表（Q6 已确认）。
2. **粗切**：层次化第一级——把字幕全文切成"话题段"（Q5 的 C 方案；
   便宜预筛 + LLM 精修以控制成本）。
3. **细切**：在话题段内做"切片友好片段"细切（Q2 已确认：两级都要）。
4. **辅助信息定位**：视觉与弹幕按 Q1 的结论接入（已确认：并存两级，视觉镜头段保留）。
5. **UI 与报告跟进**：话题段导航 + 切片候选展示与复核。
